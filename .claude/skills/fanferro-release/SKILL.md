# Releasing fanferro

Versioning: SemVer, one version for the whole workspace (`Cargo.toml` `[workspace.package].version`
and the `fanferro-core` workspace dependency); the Python package reads it from the binding crate.
While 0.x, breaking changes bump the minor version (`scripts/release.py major` does that too; pass
`1.0.0` explicitly to leave 0.x).

## Normal flow (GitHub)

1. Actions → **Prepare release** (`prepare-release.yml`) → enter the version (e.g. `0.2.0`) or
   `patch`/`minor`/`major`; with `gh`: `gh workflow run prepare-release.yml -f version=0.2.0`. It
   runs `scripts/release.py`: bumps the versions, refreshes `Cargo.lock`, and adds a
   `CHANGELOG.md` section generated by git-cliff (`cliff.toml`) from the conventional commits since
   the last tag (hand-written notes under `[Unreleased]` move into it; a hand-written entry that
   names its pull request, `(#58)`, replaces the generated one, and the rest of a generated group
   joins the hand-written group of the same heading). It opens the PR
   `chore(release): v0.2.0` from the branch `release/v0.2.0`.
2. Polish the changelog section in the PR (commits on its branch) - it becomes the GitHub release
   notes. The PR description becomes the body of the release commit on main: replace the
   generated one, which tells the reviewer what to do, with the changelog section, each paragraph
   and list item on a single line (`gh pr edit <n> --body-file <section>`). Copied as wrapped in
   `CHANGELOG.md`, it comes out ragged on main (see the v0.4.0 and v0.5.0 commits). Then
   **squash-merge**.
3. **Tag release** (`tag-release.yml`, on the merged `chore(release): v…` commit) creates the tag
   and dispatches the release workflow for it.
4. **Release** (`release.yml`, also runs when a `v*.*.*` tag is pushed by a person):
   - verifies tag == Cargo version and that CHANGELOG.md has the section;
   - builds wheels with `--profile dist`: Linux x86_64/aarch64 × manylinux2014/musllinux_1_2
     (maturin + zig), macOS arm64/x86_64 (11.0+), Windows x64, Windows arm64 (best effort: may
     fail without blocking the release), and the sdist (also built and smoke-tested from source);
   - smoke-tests every wheel natively with `scripts/smoke_test.py` on Python 3.12 and 3.15
     (musl wheels in Alpine containers, Python 3.12 and 3.14);
   - creates the GitHub release (pre-release while 0.x) with build provenance attestations and
     notes from `scripts/release_notes.py`;
   - publishes to PyPI with trusted publishing when the variable `PUBLISH_TO_PYPI` is `true`.

To rebuild or retry a release for an existing tag: Actions → Release → Run workflow → tag `v0.2.0`
(`gh workflow run release.yml --ref v0.2.0 -f tag=v0.2.0`, as `tag-release.yml` does).

## One-time repository setup

- PyPI: add a trusted publisher for project `fanferro`: owner `kalaspuff`, repository `fanferro`,
  workflow `release.yml`, environment `pypi` (use a "pending publisher" before the first upload).
- GitHub: create the environment `pypi` (optionally restricted to tags `v*` and required
  reviewers), then set the repository variable `PUBLISH_TO_PYPI=true`.
- Optional: a `RELEASE_TOKEN` secret (fine-grained PAT or GitHub App token with contents and pull
  request write access) so release PRs trigger CI; without it the PR has no checks.
- Allow only squash merges, with the PR title as the commit title (Settings → General → Pull
  Requests: disable merge commits and rebase merging; default squash message "Pull request title
  and description"; automatically delete head branches). PR titles become commit messages and
  changelog entries, descriptions their bodies; `pr-title.yml` enforces conventional titles. A
  merge commit still tags the release, but its message ("Merge pull request #…") lands on `main`.

## Locally

```bash
uv run --no-project scripts/release.py 0.2.0     # bump versions, refresh Cargo.lock, write CHANGELOG.md
python3 scripts/release_notes.py 0.2.0           # preview the release notes
make wheels                                      # Linux wheels into target/wheels (build-wheels)
uv run python -I scripts/smoke_test.py           # what the release runs against each wheel
```

Commit as `chore(release): v0.2.0` through a PR; pushing a tag `v0.2.0` by hand also releases.

## Checks before releasing

- `make check` green on main; the changelog section reads well for users (it is the release notes).
- `fanferro guide` content matches the release (it ships in the wheel).
- For breaking changes: migration notes in the changelog and an ADR if a wire format changed.

## Troubleshooting

| Symptom | Fix |
| --- | --- |
| "tag vX does not match Cargo.toml version" | The tag points at a commit without the bump; delete the tag, release from the merged bump commit |
| "CHANGELOG.md has no '## [X]' section" | Add the section on main through a PR, re-tag (or re-run with the new tag) |
| "tag vX already exists" in Tag release | The version was released already; prepare a new version |
| A release job failed and nothing was published | `release.yml` runs from the tag, so a workflow fix needs a new tag: fix on `main`, delete the tag (`git push origin :refs/tags/vX`), re-tag the fixed commit and run Release for it |
| Windows arm64 job failed | Best effort: the release continued without that wheel; fix in a patch release |
| PyPI job skipped | `PUBLISH_TO_PYPI` is not `true`, or the GitHub release job failed |
| PyPI "invalid-publisher" | The trusted publisher must name workflow `release.yml` and environment `pypi` |
